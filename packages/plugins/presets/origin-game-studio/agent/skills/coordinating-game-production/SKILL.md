Divide independently ownable work after the graph identifies its inputs and
consumers. The coordinating Session remains an ordinary Session, not a Host
supervisor. Use available create/send/read messaging tools; no wait/join,
durable inbox, lifecycle manager or native worktrees.

First make the ordered `greybox` milestone playable before dividing asset
batches and later systems. Assign a bounded movement/interaction slice, not
the whole systems backlog to be finished before launch. Keep milestones named
for what the person will experience, and announce the next playable outcome
as work moves. Unknown remaining work is unknown; do not estimate a completion
time from tool count. Use real pending elicitation requests for questions and
include complete recommended answers; do not create another waiting list.

## Choose the right collaboration unit

Use a short SDK subagent for bounded reading, comparison, diagnosis or advice
whose result fits in a sourced answer. Use a peer Thread for substantial
writes, its own checkpoints, open questions, or work the person may steer
independently. Parallelism is useful for disjoint tasks with ready inputs;
it cannot make an unverified skeleton, interface or exporter ready sooner.
An ordinary coordinator continues independent work while peers work and
reads/messages them when integration needs their results.

## Architecture before allocation

Read the graph's full scope, journey matrix and current production brief.
Identify the shared-source contract: module interfaces, IDs, asset conventions,
units/axes, events, tuning ownership, imports, paths and consumer expectations.
Assign one owner to each shared contract and assembly file. Native Threads
share the checkout and `main`; they do not have isolated branches. Allocate
disjoint write paths, including generated files, manifests and shared assets.
Request a change from the owner rather than racing to edit their file.

For uncertain designs, use an arena of bounded alternatives: compare concrete
proposals against the same sources, criteria and consumer constraints. Keep
the comparison in graph references/evidence; do not create duplicate specs or
parallel production implementations. Choose on evidence, not vote count,
number of agents or polish of the explanation. Prove the selected method in
an end-to-end pilot before distributing batch work.

## A complete, bounded brief

Send each peer the following in ordinary prose, referencing the authoritative
records rather than cloning them into a new schema:

- Outcome and graph node IDs, exact source/plan revision, accepted direction,
  required route and acceptance criteria; state non-goals.
- Inputs already inspected: source paths, reference/artifact IDs, versions,
  relevant tool results and known counterexamples. Do not delegate the
  coordinator's missing understanding as “investigate and fix everything.”
- Exclusive write paths and files owned by others, shared interface contract,
  safe checkpoint scope and what changes require contacting another owner.
- Named consuming module and owner, expected export/API format and the
  integration action that makes the output useful.
- Verification to execute, evidence to preserve and the precise return shape:
  commands/tool calls with decisive outputs, source/export revisions, artifact
  paths, inspected findings, outstanding defects and consumer handoff.

For example, a character producer receives a specific reference and verified
skeleton revision, owns that character's source/export directory, and returns
an engine-imported locomotion sample to the animation owner. They do not own
the shared animation registry or claim the campaign works because the clip
plays. A level worker receives the entry/exit contract and must demonstrate
the normal transition, not return a `goto` screenshot of the destination.

## Integration and independent critique

Commit bounded coherent work without staging a peer's changes. Never reset,
revert or overwrite unexpected shared-checkout work. If edits collide, the
coordinator reads both intents and reconciles with their owners promptly.
Checkpoints are ordinary kept checkpoints, not technical approval gates.
This workflow introduces no PR, Graphite stack or plugin machinery.

The integration owner checks returned evidence against the actual changed
source, consumes the asset/module, then verifies the affected journey. A
worker saying “done” is not evidence that an import path exists or that a
module is called. Recheck after shared dependencies change; old proof stays
historical and never silently becomes proof of the new revision.

Give independent critique a concrete claim to try to refute, the exact
artifact/build, sources and relevant criteria. Ask for observable defects,
locations and reproduction evidence, not a broad approval. Reproduce findings,
fix what is real and record what remains uncertain. The critic does not gain
permission authority and a clean critique does not replace live verification.

Keep decisions in the graph and evidence in its existing linked records;
do not introduce a second plan, approval-learning ledger or automatic refine
loop. Return product choices to the person through the existing plan decision
when the required scope or direction changes, while resolving routine
technical work within the accepted plan.
